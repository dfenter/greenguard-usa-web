SparkInflux

Stop losing InfluxDB history when a page cap fills up

The InfluxDB historian on Ignition today can silently delete history once it fills up, and a wide trend can make the gateway's memory climb while it loads. SparkInflux is coming to remove both problems, with an outage that never costs you a point and reads that stream instead of stall.

Point it at the bucket. Nothing waits on a page cap again.

SparkInflux writes the same data layout the existing InfluxDB module uses, so pointing it at data you already have is a configuration change, not a migration. If the server goes away, points are held safely instead of being lost when storage fills up, and nothing is deleted on overflow. When the server comes back, everything drains on its own with nothing missing.

A wide trend streams back row by row instead of loading the whole result before showing the first point, so opening a report does not make the gateway's memory climb.

For your engineers

SparkInflux registers as a Tag Historian provider on 8.1 and a Historian extension point on 8.3, writing the same line-protocol schema the existing InfluxDB module uses. Writes are gzip compressed by default and pipelined across several in-flight requests instead of one synchronous call. Points held during an outage sit on a disk ring rather than a page reloaded fully into heap; overflow is quarantined, not discarded. Reads stream row by row, and common aggregates push down into Influx's own query engine rather than being computed after the fact in the gateway. Load gate figures: 49,814 pts/s sustained write, a 1,500,000-point outage-and-recovery cycle with zero loss, and a 10,000,000-point bulk write with heap-flat streaming reads (193 MB used, -Xmx1g cap).
