SparkInflux

InfluxDB, written from Ignition without a page cap or a silent delete

The InfluxDB historian on Ignition today comes from a 28 MB module built on a synchronous writer, a page cap that deletes history when it overflows, and reads that materialize the whole result before your script sees a row. SparkInflux is the same InfluxDB backend, a different write and read path.

Point it at the bucket. Nothing waits on a page cap again.

SparkInflux registers as a Tag Historian provider on 8.1 and a Historian extension point on 8.3, writing the same line-protocol schema the existing InfluxDB module uses so pointing SparkInflux at data written by that module is a config change, not a migration. Writes are gzip compressed by default and pipelined across several in-flight requests instead of one synchronous call, flushed on a size or time trigger.

If the server goes away, points are held on a disk ring instead of a page reloaded fully into heap, and nothing is deleted when the ring fills; overflow is quarantined, not discarded. When the server comes back, the ring drains on its own. Reads stream row by row instead of materializing the full result, and common aggregates push down into Influx's own query engine rather than being computed after the fact in the gateway.

Four Situations This Solves

All four come from the write and read path underneath the existing InfluxDB module, not from InfluxDB itself.

The situationWhat changes
The historian went quiet during an outage and nobody noticed the gap
Any plant whose InfluxDB connection has ever dropped mid-shift.		 Points write to a disk ring while the server is unreachable, with nothing lost and nothing silently deleted when the ring is under load. On reconnect the ring drains on its own; the outage-and-recovery load scenario measured a 1,500,000 point backlog drained in just over 20 seconds with zero loss.

A team that already has InfluxDB history and does not want to touch it.		 SparkInflux writes the same measurement, tag and field layout by default, so pointing it at an existing bucket is a configuration change. Existing history reads without a migration step.
