KNOWN GAP, STATED PLAINLY: Host MessageOrdering

operational-behavior-host-reordering-success is NOT EXECUTED, and the three sibling SHOULD
assertions are MAYBE. Cause is a real host-side interop defect, not a harness gap. Our Host
requires an alias on EVERY non-control BIRTH metric, but aliases are OPTIONAL in Sparkplug
and the TCK's Tahu-based reference edge aliases only one metric; it also rejects a UINT32
metric whose value arrives in long_value, which Tahu emits. The reference edge's NBIRTH is
therefore rejected, the node stays unknown, its first DATA provokes a DATA-before-BIRTH
rebirth, that consumes the rebirth cooldown (sparkbridge.host.rebirthCooldownMs, 10s), and
the seq-gap rebirth the test is waiting for is suppressed. No rebirth observed means
reorder_count never reaches 1 and -success is never reached.

Both defects are on the 2.3.0 engineering list. Fixing the alias one means reworking
NodeBindings, which indexes bindings BY alias on the host's hottest lookup path, so it was
deliberately not attempted at the tail of a record session. Zero FAILs either way.
