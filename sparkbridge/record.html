SparkRecord

A record pipeline that starts from the record, not the row

Sparkplug B carries structured records as well as point values, and estates already publish JSON events on arbitrary topics and SparkFlow events on a NATS core alongside them. The standing answer in the Ignition market maps a record to a SQL row. SparkRecord is the structured record lane of the family: schema discovery, an exactly-once ledger and a SHA-256 audit chain, landed in the destination you already run.

Every record's id is a SHA-256 over its canonical JSON, chained to the one before it. No UPDATE or DELETE is ever issued by the module.

Every record lands once, in order, and proves it never changed.

SparkRecord receives three record lanes: Sparkplug B records (Cirrus Transmission Record objects, DataSet and Template metrics), JSON events on arbitrary MQTT topics through topic-to-stream templates, and SparkFlow events over NATS JetStream. Schema is discovered from the payload, versioned in a registry table, and migrated additively only, never destructively; SQL is generated per dialect.

Every value is type-validated. A reject lands in a quarantine table with the reason recorded, nothing dropped silently. Delivery is exactly once: the source timestamp is preserved separately from the receipt timestamp, producer identity rides on every row, persistence is ordered per producer, deduplication is by content hash, and the ledger entry is written in the same transaction as the record.

Three Situations This Solves

Three reasons a record pipeline stops being trustworthy, and what changes.

The situationWhat changes
A batch mapped to a row, and nothing else kept
The incumbent answer treats a record as a row and stops there.		 Mapping a record straight to a SQL row throws away the producer identity, the true source time, and any way to prove the row was never edited after landing. SparkRecord keeps the source and receipt timestamps as separate columns, stamps producer identity on every row, and computes a SHA-256 record_id chained to the row before it, so a rerun, a migration or a regulator can be answered from the table itself.
A rerun that silently doubles the dataset
A replayed backlog or a restarted consumer redelivers records that already landed.		 Without content-hash deduplication and an ordered, per-producer ledger, a replay after an outage lands the same batch twice. SparkRecord's ledger is written in the same transaction as the record, so a restart or a network drop produces neither a gap nor a duplicate.
A schema change that breaks the pipeline or drops data
A new field or a widened type either fails the job or gets silently discarded.		 SparkRecord discovers schema from the payload and versions it in a registry, migrating additively and never destructively. A value that fails type validation is not dropped: it lands in a quarantine table with the reason recorded, so nothing disappears without a trace.

SparkRecord fits any estate that already produces structured records or events and needs them to land somewhere durable, provable and destination-agnostic. All five destinations ship in the same license: PostgreSQL, SQL Server, TimescaleDB, Snowflake, and S3-compatible object storage.

For your engineers

The consumer core reuses MqttTransport, PayloadCodec and DiskBuffer from io.sparkbridge:common for the two MQTT lanes; SparkFlow arrives on NATS JetStream as its own consumer. The schema registry generates DDL per dialect and migrates additively and widening-only. The append-only writer commits the ledger row in the same transaction as the record: ordered per producer, deduplicated by content hash, source and receipt timestamps stored separately. A standalone verify CLI re-walks any table, checks every record_id and prev_hash, and reports the first break. It runs on the SparkBridge Host and Edge described on the technology page.

Inside the family, SparkVault is the tag historian: time series, trend readback, replay. SparkRecord is the structured record and event lane. SparkInject is the cloud lakehouse feed.
