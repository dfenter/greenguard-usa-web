conformance

Tested Against the Official Suite

The Eclipse Foundation, who publish the Sparkplug specification itself, also publish its official examiner: a test kit that watches a product on the wire and fails it for any deviation from the standard. Here is what that looked like, in plain terms.

What was tested

Not a simulation and not a paper claim. A complete live system was stood up, broker, host and edge together on a real Ignition gateway, and the official kit connected to it like any other participant, watching every message. It then put the system through the situations that break integrations in the field: publishing complex equipment models with parameters and datasets, receiving and acting on commands, losing the central server mid-session, and being forced to walk from one broker to another without losing its devices.

How it judges

The kit reads every byte the modules put on the wire and checks it against the specification: message order, sequence numbers, birth and death certificates, retained state, timing. There is no partial credit; a single wrong byte or out-of-order message fails the scenario.

The result

The newest record is the 2026-08-15 seed-240 session against 2.4.0 code: ten runs, zero FAIL lines anywhere in the session, 182 EDGE assertions passed and 52 HOST assertions passed, with a single MAYBE against an optional SHOULD. The earlier 2026-08-14 record of 346 assertions executed and 346 passed, zero failed, across every edge profile and the host session profile, stands as history. Every run is scripted and repeatable, and the nine-profile session is now a single command, so the result can be reproduced on your own hardware rather than taken on trust.

Where the formal listing stands

The engineering is done: the examiner passes, on demand, on your hardware. What remains is the administrative half of the Eclipse Foundation listing, which is membership, paperwork and a published report, and it is in progress. We say this plainly because the listing is a third party's to grant, and you should be able to tell the difference between a vendor who has passed the tests and one who says the word certified.

The full execution record is published, raw and unedited, at the TCK results page; the whitepaper carries the analysis.

The Specification

A profile over existing standards, not a new wire protocol: every requirement is expressible with a conformant OASIS MQTT 5.0 client and broker, and strict mode remains Sparkplug 3.0 conformant. This page renders the complete normative text; the file of record ships with the source as docs/SB-MQTT5-SPEC.md.

Short definitions of the message types and terms are on the technology page glossary.

Three conformance classes, one degradation rule

An implementation claims one or more classes. R and C extend S and MUST degrade to S by configuration alone: no code change, and no redeploy of peers.

CLASS S Strict. Sparkplug 3.0 wire semantics on protocol 3 or 5. The TCK-eligible class, and the default: Clean Start 1, Session Expiry 0, Will Delay 0.

CLASS R Resilient Edge. Flap-immune Wills, session-resume NDEATH suppression, and data expiry for edges on unreliable links. Protocol 5 only; edge transports only.

CLASS C Coordinated Host. Shared-subscription consumer groups feeding one host-side projection, for fan-in beyond a single consumer. Protocol 5 only; disabled for TCK runs.

1. Normative references and landscape

Spec Status Role here

MQTT 5.0 is the terminal wire target for this generation. Differentiation comes from how completely and correctly the v5 feature set is exploited (the incumbent commercial modules are 3.1.1-only end to end).

1.1 Conformance classes (∆C new)

An implementation claims conformance to one or more classes. Classes R and C are extensions of Class S and MUST degrade to Class S by configuration alone (no code change, no redeploy of peers).

  • Class S - Strict. Mode S sessions (§3), Sparkplug 3.0 wire semantics (§4), on protocol 3 or 5. This is the TCK-eligible class. Status (∆E): VERIFIED - Eclipse Sparkplug TCK 3.0.0 certification session of 2026-08-15 (seed 240, ten runs, zero FAIL lines): EDGE profile 182 PASS including device-level, PrimaryHost and MultipleBroker tests; HOST profile 52 PASS including MessageOrdering; SessionTermination run on BOTH protocol 3 and protocol 5, closing the protocol-5 Mode S coverage item. One SHOULD-optional MAYBE (payloads-metric-datatype-not-req). Method + results in docs/TCK.md and tck/run-full-session.sh. Class S carries the R-7 auto-reconnect bdSeq deviation (§14) - the TCK does not exercise mid-session reconnects.
  • Class R - Resilient Edge. Class S host + Mode R edge transports (§3 Mode R): flap-immune Wills, session-resume NDEATH suppression, data expiry. Protocol 5 only.
  • Class C - Coordinated Host. Shared-subscription consumer groups (§6 B-3) feeding ONE host-side projection. Protocol 5 only; disabled for TCK runs.

2. Protocol support

  • P-1 Every transport MUST support MQTT 3.1.1 and 5.0 behind one API (sparkbridge.mqtt.protocol, per-transport override).
  • P-2 Mixed fleets MUST interoperate through the broker (MqttV5Test).
  • P-3 The v5 backend MUST wrap its exception type so call sites are protocol-agnostic.

3. Session modes

One knob: sparkbridge.mqtt.sessionMode = strict (default) | resilient.

Mode S - strict (Sparkplug-certified)

  • S-1 Clean Start MUST be 1 (v3: cleanSession=true), Session Expiry 0, Will Delay 0.
  • S-2 Mode S MUST be the default and MUST be used for TCK runs, with shared-subscription consumer groups DISABLED (a fleet of independent shared consumers each sees only a fraction of DATA and cannot maintain complete Sparkplug state; shared mode is a coordinated-host extension, §6).
  • S-3 Mode S is valid on protocol 3 and 5 (Sparkplug 3.0 permits v5 clients with these settings): certification does NOT require 3.1.1.

Mode R - resilient (flap-immune edge; EDGE-ONLY)

  • R-0 Mode R applies ONLY to edge-node transports. Host transports MUST remain Mode S regardless of configuration; the implementation keys this off the Will: only a NON-retained Will (edge NDEATH) activates Mode R connect behavior, so a host's retained STATE Will automatically gets strict semantics. Rationale: resumed host subscriptions + inflight redelivery would violate host session-establishment ordering.
  • R-1 Protocol 5 only. Configured with protocol 3, the transport MUST warn and operate as Mode S.
  • R-2 The edge NDEATH Will MUST carry Will Delay Interval D = sparkbridge.mqtt.willDelaySec (default 5 in Mode R), Session Expiry MUST equal D, Clean Start MUST be 0. A same-client reconnect within D resumes the session, which cancels the pending NDEATH (a clean-start reconnect ENDS the session and fires it - verified against HiveMQ). The client MUST read the CONNACK's effective Session Expiry Interval and Session Present flag where the client library exposes them, and MUST warn if the server reduced Session Expiry below D (the Will can then fire earlier than configured).
  • R-3 Retained Wills (host STATE) MUST NOT be delayed.
  • R-4 (∆D terminology) The resumed MQTT session MUST carry no queued QoS 1/2 deliveries and no server-side inflight - only the pending Will (subscriptions MAY persist across the resume; MQTT keeps them as session state). Concretely: in Mode R the edge's subscriptions are QoS 0 (no broker-side queueing for the gap) and edge data SHOULD be published QoS 0, so session resumption carries no queued deliveries and no server-side inflight. Client-side unacked QoS 1 publishes from before the drop MAY be retransmitted by the client library after resume; the host's seq handling (gap → rebirth, cooldown-limited) absorbs this, and store-and-forward replay remains gated on a fresh primary-host STATE. A fresh NBIRTH MUST be published on every reconnect (see R-7 for bdSeq).
  • R-5 D MUST be < sparkbridge.host.deadNodeTtlMs (default 300s) and SHOULD be 2–10s.
  • R-6 Operators MUST size comms-loss alarms on: broker keep-alive detection time (~1.5 × keepAlive) + D, plus broker-restart edge cases where the spec permits later Will publication.
  • R-7 bdSeq/Will lifecycle with library-managed auto-reconnect: the Will registered at CONNECT carries the session bdSeq; automatic reconnects reuse that Will, so the edge MUST keep the SAME bdSeq for rebirth NBIRTHs across auto-reconnects of one logical session (Will/NBIRTH bdSeq consistency outranks per-connection increment, which would orphan the registered Will). bdSeq MUST increment on every fresh online() (process restart persists via the bdSeq store). This is a documented deviation from a per-MQTT-connection increment reading of Sparkplug. (∆D scope corrected - Rev C claimed it was invisible in Mode S; it is not.) It applies under library-managed auto-reconnect in ALL session modes: a Mode S auto-reconnect opens a NEW MQTT connection whose rebirth NBIRTH still carries the session bdSeq (EdgeNode.onReconnect). The TCK does not exercise mid-session reconnects, so Class S verification does not cover this path; ledgered in §14.

The persisted edge counter is intentionally full-width and monotonic; only the final wire encoding is reduced to Sparkplug's required unsigned byte. Hosts therefore match an NDEATH to the current session by the pair (wire bdSeq, NBIRTH/NDEATH session timestamp), not by comparing the byte modulo 256 across the node's history. This prevents an old NDEATH carrying wire bdSeq=0 from fencing a current session after the internal counter crosses 255. A death whose pair cannot be verified is ignored while a current session is resident.

4. Message classes: QoS, expiry, retain

Class QoS Retain Message Expiry Notes
NBIRTH/DBIRTH/NDATA/DDATA/NCMD/DCMD (wire publishes) 0 no see below Sparkplug 3.0 mandate; seq/rebirth provide recovery
NDEATH (Will registration) 1 no never Sparkplug-mandated
STATE 1 yes never retained liveness flag
S&F replay NDATA 1 (∆D profile deviation, §14) no NDATA policy replay only while host online (§4.1)
UNS JSON 0 optional NDATA policy current-value stream

Expiry policy (MQTT 5 connections only):

  • M-1 Expiry properties MUST be silently omitted on v3 connections and MUST be omitted (not sent as 0) when disabled - a wire value of 0 means zero lifetime, not "no expiry".
  • M-2 BIRTH/DEATH/STATE MUST never carry expiry, in any mode.
  • M-3 NDATA/DDATA/UNS MAY carry sparkbridge.edge.dataExpirySec (default 0; SHOULD be 60–600 in Mode R), and NCMD/DCMD MAY carry sparkbridge.host.cmdExpirySec (default 30 under protocol 5). Expiry is broker-queue hygiene, NOT a safety mechanism: it only prevents the broker starting onward delivery after the interval. It does not bound client-side queue aging, near-deadline delivery, or QoS 1 duplicates. Command execution guarantees MUST come from the application layer: Host.sendCommandConfirmed (write-back confirmation) is the mechanism; deployments where a late "safe-stop" expiring would preserve an unsafe state MUST set cmdExpirySec=0 or use confirmed writes.
  • M-4 (∆C RESOLVED; ∆D reworded) Rev B shipped NBIRTH/DBIRTH and NCMD/DCMD at QoS 1; the TCK flagged all of them (payloads-nbirth-qos, payloads-dbirth-qos, topics-ncmd-mqtt, payloads-ncmd-qos). The BIRTH/DATA/CMD wire publishes (first table row) are now QoS 0 as Sparkplug mandates (commit e5400f6); NDEATH Will registration and STATE remain QoS 1 as Sparkplug itself requires. S&F replay is the one remaining QoS deviation (§14). Delivery/execution assurance for commands comes from M-5, never from MQTT QoS.
  • M-5 (∆C new, promotes shipped behavior to normative) sendCommandConfirmed MUST verify that the edge's reported value matches the requested write (not merely that the metric changed), MUST stamp waiters with the connection epoch at pre-publish capture and refuse confirmation from reports received after a reconnect (the QoS-0 command died with the session), and MUST fail all pending waiters on connection loss. (∆D) Epoch fencing is the hard guarantee - no post-reconnect report can falsely confirm - but the failure notification itself is dispatched through the reconnect work queue and MAY lag the connection loss; callers MUST rely on fencing plus their own timeout, not on prompt failure delivery.

4.1 Store-and-forward replay (∆C new, promotes shipped behavior)

  • SF-1 Offline-buffered data MUST be encoded at capture time (source timestamps frozen) and flagged is_historical; the host MUST project historical values with their source timestamps so history backfills a real curve, not an arrival-time burst.
  • SF-2 (∆D "fresh" defined) Replay MUST be gated on a primary-host STATE online message observed on the CURRENT transport connection epoch, after (re)subscription - retained or live delivery both qualify; a STATE observation from a prior epoch MUST NOT arm replay. A fresh NBIRTH MUST precede any replayed data.
  • SF-3 Replay semantics are at-least-once: the disk buffer maintains a crash-persisted read cursor; duplicates after a crash are permitted and absorbed by host-side handling. Poison (undecodable) records MUST be dropped, not wedge the replay.

5. Flow control and sizing

  • F-1 The client MUST honor the broker's CONNACK Receive Maximum and Maximum Packet Size for outbound traffic (delegated to the client library; wire-limit guards keep payloads bounded far below broker frame limits). CONNECT Maximum Packet Size MAY be set to bound inbound packet size; packet size includes topic + properties overhead, not just payload.
  • F-2 (∆C updated to shipped design) Receive Maximum bounds unacknowledged QoS 1/2 inflight per network connection; it does not constrain QoS 0 and does not bound application worker queues, because the client library acknowledges on arrival, before application processing. Real backpressure in SparkBridge is the bounded per-shard dispatch queues - bounded by BYTES as well as count, with counted shedding for data. (∆D routing described as implemented) BIRTH/DEATH normally execute in order on the shard workers; when a shard budget would reject them they overflow to a dedicated unbounded control executor instead of being shed, and reconnect/connection-loss callbacks always run on the control executor. Control traffic is bounded only by a separate pathological-flood byte ceiling whose breach is ERROR-logged. sparkbridge.mqtt.receiveMax remains available as an inflight-window tuning knob (0 = library default) and MUST NOT be documented as a queue guarantee.
  • F-3 Topic aliasing is directional. sparkbridge.mqtt.topicAliasMax (default 16) advertises the inbound allowance (aliases the broker may use toward this client). (∆D) MQTT 5 does NOT require the broker to use or match this value; deployments that want inbound aliasing effective SHOULD configure the broker's per-client allowance ≥ this value (the reference HiveMQ config does). Outbound aliasing (client → broker) is governed by the broker's CONNACK Topic Alias Maximum and only takes effect if the client library originates aliases; the profile treats outbound aliasing as opportunistic, not required.

6. Subscriptions

  • B-1 v5 non-shared subscriptions MUST set noLocal EXCEPT STATE-topic subscriptions: a Sparkplug host MUST receive STATE on its own host topic (including a stale offline STATE from a fired Will of a prior same-clientId session) so it can immediately republish online. The transport exempts spBv1.0/STATE/... (and legacy STATE/...) filters from noLocal. (∆D) The exemption is DEFINED on those exact topic namespaces; the current implementation matches by string prefix, which also exempts non-Sparkplug sibling filters (e.g. spBv1.0/STATEFUL/#)
  • harmless to Sparkplug traffic, ledgered as a residual in §14.
  • B-2 $share subscriptions MUST NOT set noLocal (MQTT 5 protocol error); the guard lives in the transport.
  • B-3 Shared-group consumption (BIRTH/DEATH/STATE broadcast non-shared; NDATA/DDATA shared; seq-gap rebirth suppressed) is a coordinated-host extension (Class C): valid because all consumers feed ONE host-side projection (shared listener/state), not N independent Sparkplug hosts. It MUST be disabled for TCK runs (S-2). Shared DATA is timestamp-guarded per managed tag path: an older source timestamp is discarded, equal timestamps remain arrival-ordered, and group-partitioned filters remain the strict- ordering option.

7. Capability negotiation

  • C-1 On a v5 CONNECT, where the client library exposes CONNACK properties, the transport MUST read and log: Session Present, effective Session Expiry, Receive Maximum, Maximum QoS, Retain Available, Shared Subscription Available, Topic Alias Maximum.
  • C-2 The transport MUST warn when a feature the deployment depends on is absent (shared subscriptions configured but not available; retain unavailable when a STATE Will is registered; effective session expiry < configured Will delay). (∆D scoped honestly) Capability handling is warn-and-proceed (diagnostic), NOT fail-closed: the dependent operation is still attempted and per-operation failures surface via C-3/D-2. CONNACK properties are read at initial CONNECT only - they are not re-read after a library-managed auto-reconnect (residual, §14).
  • C-3 A failed subscribe (SUBACK failure reason) MUST be surfaced as an error with its reason code, never silently degraded.

8. Diagnosability

  • D-1 Every v5 transport MUST record the last broker DISCONNECT reason (code + string) and count disconnects and v5 client errors.
  • D-2 Every failed v5 connect/subscribe/publish MUST log its reason code before wrapping the exception.
  • D-3 The Host /metrics endpoint MUST export sparkbridge_mqtt_v5_errors_total, sparkbridge_mqtt_disconnects_total, sparkbridge_mqtt_last_disconnect_rc for the host's own transports; the Edge module MUST expose the same per node via /status. (∆C) As of v2.1.0 these endpoints (/status, /metrics, /nodes) are authenticated - scrapers MUST present the REST token (Authorization: Bearer accepted).
  • D-4 These surfaces diagnose each module's OWN broker connection. A host cannot see a remote edge's disconnect reasons (brokers do not relay them); fleet-level "why did site X drop" diagnostics come from that edge's own /status (reachable via its gateway) or broker-side connection-event telemetry, which this profile recommends enabling where the broker offers it.

9. Identity and lifecycle

  • I-1 Client IDs MUST be stable and unique per logical node (existing scheme: sparkbridge-edge-<group>_<edge>, sparkbridge-host-c<n>), and broker authentication SHOULD bind credentials to identity so a foreign client cannot manipulate a session (∆D corrected: a same-clientId SESSION-RESUMING reconnect cancels a pending delayed Will, while a clean-start takeover ends the session and FIRES it - see R-2; credential binding prevents a foreign client from doing either). (∆C, ∆D scoped) Production DEPLOYMENTS MUST use per-edge credentials with broker ACLs scoped to each edge's own topic namespace (sparkbridge.broker.edgescopes; per-edge RBAC template in broker/hivemq/credentials.xml). This is a broker-deployment requirement: the shipped modules configure one edge credential set per gateway (sparkbridge.edge.username), so identity granularity is per-gateway today and per-node granularity is enforced at the broker. A single shared edge identity with a wildcard ACL is a development-only configuration (fleet spoofing risk).
  • I-2 The Will for a session MUST be built immediately before its CONNECT with that session's bdSeq (edge) or a fresh timestamp (host), and the host's online STATE published after CONNECT MUST carry the SAME timestamp as the offline STATE registered in the Will, so consumers can order/discard stale STATE.
  • I-3 (∆D corrected - Rev C required a fresh timestamp the implementation deliberately does not use) After a library-managed auto-reconnect, the host re-announces online STATE carrying its CONNECT-TIME timestamp - the same one registered in the Will, per I-2 and I-5. Timestamp ordering across host sessions is established at CONNECT, not per-publish; within one session the online/offline pair shares one timestamp, and I-5's single-re-assert rule prevents stale-STATE flapping. Edge-side STATE consumers SHOULD ignore STATE messages older than the newest seen.
  • I-4 (∆D) Graceful shutdown MUST make the death visible by one of two mechanisms: (a) publish the explicit death (edge NDEATH / host retained offline STATE) and then disconnect normally, or (b) on MQTT 5, DISCONNECT with reason 0x04 "Disconnect with Will Message" so the broker publishes the registered Will. The implementation uses (a); (b) is a conformant alternative this profile permits. If the explicit death publish fails, the client SHOULD NOT complete a normal disconnect - that suppresses the Will and loses the death entirely (known residual, §14). Hosts MUST tolerate duplicate deaths (explicit + Will) idempotently.
  • I-5 (∆C new, promotes TCK-driven fixes to normative) While online, a host that observes an offline STATE for its OWN host id MUST republish its online STATE (with its connect-time timestamp per I-2), exactly once per observation - no republish loop. All STATE online/offline publishes MUST be serialized under one lock across start/reconnect/graceful-offline/inbound-STATE paths so a racing auto-reconnect cannot overwrite a graceful offline.

10. Broker requirements

MUST support: MQTT 5.0, shared subscriptions, Will Delay, Message Expiry, Session Expiry ≥ 10s, topic aliases ≥ 16/client. HiveMQ CE (reference config broker/hivemq/config.xml) satisfies all; embedded Moquette satisfies none of the v5 items and stays a DR-only fallback outside this profile. (∆C) When TLS is configured, the plaintext listener MUST be disabled - the v2.1.0 default; (∆D) the explicit sparkbridge.broker.plaintext=true override exists for migration/debug and MUST NOT be set in production. The Sparkplug TCK extension MUST NOT be enabled on production or benchmark brokers (measured: 96% delivered-throughput collapse, 2.2 GB log in minutes).

11. Security

Unchanged from v2.x (TLS + hostname verification on ALL secure URIs, optional mTLS, broker RBAC per I-1, secrets file with fail-closed read + chmod 600 enforcement, token-gated REST per D-3). MQTT 5 Enhanced Authentication is OUT OF SCOPE for this version (file-RBAC + mTLS covers the threat model).

14. Known deviations and residuals (∆C reframed; Rev B's build plan

N-1..N-9 is complete and folded into the sections above)

Documented deviations from the Sparkplug 3.0 letter:

  • R-7 (∆D scope corrected) bdSeq held constant across library auto-reconnects of one logical session - ALL session modes, not only Mode R. Accepted because Will/NBIRTH bdSeq consistency outranks a per-connection increment (which would orphan the registered Will). Not exercised by the TCK; revisit if a future TCK revision flags it.
  • S&F replay QoS (∆D new entry) replayed NDATA publishes at QoS 1 (delivery pragmatics for buffered history over lossy links) vs Sparkplug's QoS 0 letter; replay does not occur in TCK configuration.
  • B-3 shared-group consumption (Class C only; disabled in TCK configuration). Shared DATA is timestamp-guarded per managed tag path: a source timestamp older than the last-written source timestamp is discarded, equal timestamps remain arrival-ordered, and group-partitioned filters remain the strict-ordering option when per-edge ordering is required.

Open residuals, first ledgered at v2.1.0/Rev C and carried through each release review since (v2.4.0 ledger: docs/internal/RELEASE_REVIEW_2.4.0.md; non-blocking): sendWire swallows publish failures; Will suppressed on clean disconnect after a failed offline publish (violates I-4's SHOULD); PayloadCodec nested-Template metric-bomb bypass; DiskBuffer DATA-after-prune bounded oscillation; dev broker credentials template still ships a wildcard edge role; (∆D) STATE noLocal exemption matches by prefix (B-1); confirmed-write failure notification can lag connection loss (M-5); CONNACK capabilities not re-read on auto-reconnect (C-2).

Out of scope this version: enhanced auth, subscription identifiers, request/response correlation, MQTT-SN, broker connection-event telemetry.
