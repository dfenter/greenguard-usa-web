01 · the wire

One Machine, Watched From Anywhere

This is the smallest deployment, and every larger one on this page is built from it. A machine on your floor becomes a number your office can see. A change your office makes reaches the machine.

A PLC connects to the plant's existing Ignition server through Ignition's own driver; that server keeps its local database. The SparkBridge Edge module on that server publishes its tag tree to SparkBridge Provider. A central Ignition server running the SparkBridge Host module subscribes and rebuilds the tree as a managed tag provider, which Perspective reads. A write on the central server travels back as a Sparkplug command to the site server and on to the PLC.

02 · the plant

Keep the Server You Already Paid For

Your plant already runs its own server and its own database, with local screens and local alarms. SparkBridge does not replace any of that. It replaces the slow, fragile link that copies data to your office, and hands the plant the whole company's view back.

Today · history written twice, tags fetched over the Gateway Network

Today the plant Ignition server drives the PLCs, runs local Perspective and alarms, and writes history through a splitter to both the local database and, over the WAN, to a central database. Separately the central Ignition server pulls the plant's tags over the Gateway Network. The plant holds a credential to the central database, the central database takes one connection per plant, and a WAN outage queues SQL rows in the splitter's store and forward until it comes back.

With SparkBridge · one wire up, the plant keeps its database

With SparkBridge the plant Ignition server keeps its drivers, Perspective, alarms and local database. The history splitter's remote leg is retired: the SparkBridge Edge module publishes the plant's tag tree to SparkBridge Provider with store and forward, and the central Ignition server rebuilds it through the Host module while SparkVault writes central history with the plant's original timestamps. 03 · the data center

One View of Every Site, Not a Different Screen for Each

Large operators run several separate servers because one cannot hold every site, and every team has to know which server owns which site. That slows down every decision and every new hire. SparkBridge turns those separate servers into one view, with one Host gateway that grows as you add sites.

Today · per-backend fan-in over the Gateway Network

Today, forty plants, each a full Ignition server with a local database, connect over the Gateway Network to several separate Ignition backend servers, each holding the tags of a slice of plants, while each plant's history splitter also writes rows to a central database. Application servers must query each backend separately, and each backend is a single point of failure for its slice.

With SparkBridge · one namespace, a pool of hosts

With SparkBridge, each plant server keeps its local database, runs the Edge module and publishes to a central SparkBridge Provider pair; SparkVault on the central pool writes central history once. 05 · history and the twin

Every Day, on Record and Replayable

Both your history and your live model live on the central server. Neither touches a site. History is kept on your own clock, so an outage never leaves a hole and any past day can be replayed. The live model is the same data, always current, for the tools that need it.

The central Ignition host pool receives the estate from SparkBridge Provider. SparkVault on the central server writes every value with its original timestamp to a Timescale database and can replay any window back onto SparkBridge Provider under a separate replay group. SparkFlow on the same server projects the estate onto NATS: a last-value bucket, a model bucket built from birth certificates and templates, and subjects the company subscribes to. Passage exposes the same tree over OPC-UA. Together those form the digital twin. Perspective trends read SparkVault through the ordinary tag history provider.

06 · the ultra large estate

Two Hundred Plants, One Namespace, No Ceiling

Past a certain size, no single server can hold everything. SparkFlow, its own license, is how the largest companies scale past that ceiling: each region keeps what its own operators watch, and the whole company still reads one namespace with nothing left out.

Two hundred plant Ignition servers, each with its own database, publish through regional SparkBridge Provider pairs. Each region has a central Ignition host pool running the Host module and SparkFlow: the pool keeps a managed provider of the tags that region's operators watch, and SparkFlow publishes every decoded metric onto the region's NATS server as uns subjects with a last-value bucket and a model bucket. A NATS hub sources each region's stream, so the company namespace is the union of the regions. SparkVault at the hub ingests the JetStream stream into one Timescale history, SparkInject streams it to the warehouse, analytics and AI pipelines subscribe directly, and a Perspective dispatcher tier reads live values on demand without a tag behind them. Commands travel back as uns.cmd request and reply, authorized by broker rules generated by SparkID.

07 · running it

Forty Sites, Run and Proven From One Chair

This is what running the estate from section 03 looks like day to day. One team pushes a change to every site at once. Access is generated instead of typed by hand. An outside audit checks the whole thing on demand.

A fleet publisher workstation holds the signing key and publishes retained, sequenced configuration envelopes to SparkBridge Provider. Each site Ignition server verifies the signature, refuses replay, and applies the change live. Site state travels back inside each site's birth certificate and appears on the FleetOps grid on the central server. SparkID on the same workstation generates the Provider credentials and rules. Sentinel connects to SparkBridge Provider and Host as an outsider and reports.
