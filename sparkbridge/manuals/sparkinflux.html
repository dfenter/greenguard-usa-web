SparkInflux

An InfluxDB tag-history provider for Ignition, covering both 8.1.19+ (TagHistoryProvider) and 8.3.2+ (AbstractHistorian), with pipelined writes, disk store-and-forward, and streaming reads.

1. Overview

SparkInflux is a tag-history provider that writes Ignition tag history to InfluxDB (1.8, 2.x, or 3.x) instead of Ignition's default SQL history. One codebase covers Ignition 8.1.19+ via TagHistoryProvider and 8.3.2+ via AbstractHistorian (sibling repo sparkinflux-83). Writes are pipelined and gzip-compressed by default, buffered to a disk ring during an InfluxDB outage instead of being dropped, and reads stream row-by-row with server-side aggregate pushdown instead of materializing the full result set in memory.

A gateway can run several providers at once, each with its own connection, write pipeline, and store-and-forward ring. SparkInflux is a standalone paid product, never bundled into SparkBridge itself.

2. What You Need

  • Ignition 8.1.19+ or 8.3.2+.
  • An InfluxDB server: version 1.8, 2.x, or 3.x.
  • No other SparkBridge module is required. SparkInflux is standalone with its own license.

3. Install

  1. Install the signed SparkInflux module through Config > Modules > Install or Upgrade a Module; no build step is required for the release bundle.
  2. Signed release builds need a real certificate; a development build produces an unsigned .modl that prompts the same untrusted-certificate warning on install.

4. License

Runs on Ignition's 2-hour module trial until licensed, same as every SparkBridge-suite module. Drop a sparkbridge-license.key in the gateway's data directory to lift the pause within 30 seconds; this clears the license label on status.json. Standalone paid product; never bundled into SparkBridge itself.

5. Configure

  1. Config > SparkInflux > Providers > Add. Fill in Name, InfluxDB Version (V1/V2/V3), URL, Token, Org, Bucket, then Save. The row starts its own connection, write pipeline, and store-and-forward ring immediately, no gateway restart.
  2. In Designer, open a tag's History properties, set History Provider to the provider name just created, and set a sample or scan-class rate. There is no headless gateway-web path to create or edit tag history; this step needs Designer.

Changing a row restarts only that provider; every other provider on the same gateway keeps its ring buffer and connections untouched. There is no test-connection button on the edit form; use testcreate.json or the status routes below instead.

Deadband / change-only storage

Off by default. Per tag path, a numeric value is stored if the absolute move clears Deadband Absolute, the relative move clears Deadband Percent, or Deadband Min Interval has elapsed since the last stored point. Boolean and String values are always change-only. A quality change is always stored regardless of value movement. Deadband Overrides layers per-path rules on top of the provider defaults: path=abs:0.5,pct:1,min:1000;path2=abs:2. Scripted writes via system.influx.write() deliberately bypass deadband.

Adaptive batch sizing

Off by default (fixed Batch Size otherwise). Write latency and any server Retry-After adjust the effective batch-flush threshold within the configured min/max bounds (default 500 to 50000 lines): low latency grows the batch, high latency or throttling shrinks it, adjusted at most once per 500 ms.

Scripting

system.influx.providers()
system.influx.write("influx", None, {"tagPath": "Line1/Temp"}, {"fVal": 72.4})
rows = system.influx.query("influx", 'from(bucket:"ignition") |> range(start:-1h) |> filter(fn:(r) => r.tagPath == "Line1/Temp")')
system.influx.status("influx")

Available from gateway-scope scripts: scan class, tag change script, or gateway event script.

Multi-bucket routing and config-as-code

A provider's Routing Rules field routes a tag path to the first matching prefix rule, else the provider's own Bucket. GET /data/com.sparkbridge.sparkinflux/config.json[?includeSecrets=1] returns every provider row as JSON (tokens redacted unless loopback and includeSecrets=1); POST to the same path applies the same shape idempotently by name, restarting only changed providers. Omitting token on an update leaves the existing credential untouched.

6. Operate

Day to day, watch status.json and providers.json for read/write lane health per provider. On an InfluxDB outage, writes buffer to a disk ring instead of being dropped, and drain back out on recovery; a full ring is quarantined rather than silently deleted. A malformed write (a 400 partial-write response) quarantines only the offending lines, not the whole batch. Reads use a per-provider in-memory cache for repeated aggregate queries (default 5 s TTL, capped at 50,000 rows and a configurable byte budget), invalidated the moment a write flush touches the same tag paths.

Downsampling is managed as scheduled Flux tasks via POST /data/com.sparkbridge.sparkinflux/downsample.json on v1.8/v2 providers; v3 providers return a clear unsupported-operation error since InfluxDB 3.x has no Tasks API yet.

7. Verify

  1. GET /data/com.sparkbridge.sparkinflux/selftest.json?provider=<name>&points=300 pushes real points through history storage and reads them back, returning pointsSent, pointsWritten, rowsRead, and ok.
  2. GET /data/com.sparkbridge.sparkinflux/status.json for product/version/license state, and GET /data/com.sparkbridge.sparkinflux/providers.json for per-provider read/write lane state.
  3. GET /data/com.sparkbridge.sparkinflux/schema.json?provider=<name> lists measurements, tag keys, series-cardinality estimates, and warnings (cardinality over 100,000, un-migrated Kymera-style [provider] prefixes, a measurement name mismatch).

All status/config routes are loopback-only unless sparkinflux.rest.readToken is set in the gateway's secrets file, in which case they accept Authorization: Bearer <token>.
