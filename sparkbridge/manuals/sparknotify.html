1. Overview

SparkNotify is an Ignition alarm notification profile module. It fans an alarm pipeline out to whichever combination of Slack, Teams, Telegram, WhatsApp, Twilio SMS or Voice, Discord, PagerDuty, SMTP Email, or a generic webhook a plant wants, all from the standard Ignition alarm notification pipeline mechanism. Released for both the Ignition 8.1 and 8.3 lines, built from a shared design with per-line differences noted below.

SparkNotify does not create or manage alarms; it is a delivery channel invoked from an alarm pipeline's Notification block, the same as Ignition's built-in Email/SMS notification profiles.

2. What You Need

  • Ignition 8.1 or 8.3 (separate modl per line; see 8.3 differences under Configure).
  • Credentials for whichever channel or channels you configure: webhook URLs, bot tokens, API keys, or SMTP credentials.
  • No other SparkBridge module is required. SparkNotify is standalone with its own license.

3. Install

  1. Gateway web UI > Config > Modules > Install or Upgrade a Module, upload the .modl file matching your Ignition line, accept the EULA (see license.html at the repository root).
  2. If the module is self-signed, the gateway warns about an untrusted certificate; accept or trust it to complete install.
  3. Confirm Config > Modules shows SparkNotify state = Running.

4. License

An unlicensed install runs on Ignition's 2-hour module trial clock, same as every SparkBridge-suite module. When it expires, sends stop silently with no error shown anywhere. Reset it from the gateway home page (/web/home > Reset Trial) for further trial use, or license the module for production use by dropping sparkbridge-license.key in the gateway's data directory (re-read within 30 seconds). See the README in the bundle for pricing.

5. Configure

8.1

  1. Config > Alarming > Notification > Create New Notification Profile > type SparkNotify. Create one profile per channel.
  2. Fill in the fields for the chosen channel (see table below).
  3. Designer > Alarm Notification > Rosters: add at least one user with a Contact Info entry whose type matches a configured profile's channel. An empty roster produces a log line and nothing sends.
  4. Build an alarm pipeline: Start -> Notification (profiles + roster) -> Delay -> loop back to Notification, with Acknowledged, Cleared, and Shelved set as dropout conditions.
  5. On the tag's Alarms tab, set Active Pipeline to the pipeline just built.
  6. For a gateway-scope tag alarm, set Config > System > Gateway Settings > Gateway Scripting Project to the project containing the alarm pipeline, or the alarm fires but never reaches the pipeline.

Common fields across all channels: MessageTemplate, ThrottledMessageTemplate, RepeatDelayMillis, MaxRepeats, DedupeWindowMillis, and AckEnabled, AckHmacSecret, AckBaseUrl for the acknowledge-link feature.

Ignition ships only three built-in contact types: EMAIL, SMS, and PHONE. SparkNotify maps Slack and Email to EMAIL; Telegram, WhatsApp, and Twilio SMS to SMS; Teams, Webhook, and Twilio Voice to PHONE; and defines two custom types, discord and pagerduty. A roster user routes to the first profile matching one of their contact types, so fanning out to multiple channels that share a contact type needs one roster user per profile.

8.3 differences

  • Notification profiles are configured through the newer resource-config (project/resource-based) UI rather than the legacy Config > Alarming > Notification page, depending on how the install exposes it; check both locations if the profile type does not appear where expected.
  • Per-channel roster routing on 8.3 mirrors 8.1's channel-to-ContactType mapping exactly, including the custom discord and pagerduty types, so the multi-channel fan-out above works the same way on both lines.
  • The seven credential fields (Telegram bot token, WhatsApp access token, Twilio auth token, webhook HMAC secret, PagerDuty routing key, SMTP password, ack HMAC secret) are Ignition SecretConfig values on 8.3, encrypted at rest and entered through the SECRET form field. An 8.1 profile upgraded in place has these migrated automatically; nothing needs re-entering. The three non-secret fields AckBaseUrl, EmailAllowLoopbackRelay, and EmailAllowPrivateRelay are also carried through the migration.

6. Operate

Day to day, alarms fire through their assigned pipeline and SparkNotify sends on the configured channels. Repeats continue on the pipeline's Delay loop until a dropout condition (Acknowledged, Cleared, Shelved) is met; make sure those are wired as dropout conditions or repeats never stop. Watch the per-profile status route for send failures rather than waiting for a user to report a missed alert.

7. Verify

  1. Force the tag past its setpoint. Gateway web UI > Status > Alarming > Alarm Pipelines should show Active = true, Items = 1 while unacked.
  2. GET /data/sparknotify/status.json reports per-profile status and sent counts (requires an authenticated gateway session; returns 401 if not logged into the gateway web UI first).
  3. With AckEnabled, AckHmacSecret, and AckBaseUrl all set, the delivered message includes an acknowledge link at <AckBaseUrl>/data/sparknotify/ack/link/<profile>?event=<uuid>&sig=<hmac>. Opening it returns {"acknowledged":true} and acks the alarm in Ignition.
