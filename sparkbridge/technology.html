How it works, and how it compares

For your executives: your plant data moves off the floor without loss, even when the link drops, and every gateway is bought once. Below this line is the engineering detail behind that promise, written for the team that will run it.

MQTT moves data around. Sparkplug adds what the data means, which site sent it, and whether you can still trust it. Everything the standard leaves open is where products actually differ, so this page covers the mechanism first and the comparison second.

lifecycle

The Life of One Connection

MQTT moves messages but says nothing about what is inside them. Sparkplug defines the whole life of a connection, and every guarantee it gives you comes from one specific message in that life. The list below follows the order it happens on the wire.

  1. STATE

    The server speaks first

    The host announces itself with a retained STATE message, so any site connecting later knows the consumer is alive before it says a word. Edges gate their births on it. A host restart never triggers an estate-wide stampede of uncoordinated births.

  2. NBIRTH

    The site introduces itself, completely

    The edge publishes its whole model in one birth certificate: every point with its name, datatype, engineering units and current value, stamped seq=0 and a session number that identifies this connection uniquely. Consumers learn the model from the stream itself, with no schema registry to fall out of date.

  3. DBIRTH

    Equipment arrives as whole objects

    Each device under the node announces its own metrics. A pump, a loop, a skid crosses the wire as an object with named members, not a bag of loose points, and it can be retired later without disturbing the rest of the node.

  4. NDATA

    Then, only what changes

    From here on, only changed values move, alias-only on the wire because you paid for the metric name once at birth. Steady-state load tracks what the process actually did, not how many tags exist. That is a structural property of the protocol, not a tuning parameter that decays.

  5. seq

    Every message counts itself

    A rolling sequence number rides every message, so a consumer can prove it missed something instead of quietly carrying a hole. A gap makes the host ask for the model again, rate-limited per node so one lossy link cannot amplify into a fleet-wide storm.

  6. NCMD

    Writing back is confirmed at the plant

    Commands flow the other way on the same connection. SparkBridge reports a write as successful when the site reflects the commanded value, not when the broker merely accepts the publish.

  7. NDEATH

    Silence is never mistaken for health

    The death certificate is registered with the broker as an MQTT Will at connect time, so it gets published even when the site cannot say goodbye. Every consumer knows within seconds, and values are marked stale instead of being left to look current.

  8. NBIRTH

    And the loop closes

    When the site returns it simply births again with a new session number, and everything above repeats. Recovery is the same three messages the protocol always speaks.

glossary

Sparkplug B Terms, Briefly

The words used above, defined the way the specification uses them.

Edge node
The Sparkplug client at a site that owns one MQTT session and publishes on behalf of the devices under it. In SparkBridge this is the Edge on a site gateway.
Host application (Primary Host)
The consumer that subscribes to every edge, tracks their state and is the one place commands originate. In SparkBridge this is the Host running on the Host gateway.
STATE
A retained message the host publishes to announce that it is online or offline. Edges wait for an online STATE before they birth.
NBIRTH / DBIRTH
The birth certificate of a node or a device: every metric with its name, datatype, units and current value, sent at seq 0 whenever a session starts.
NDATA / DDATA
Change-only updates for a node or device after birth, carried by alias rather than by name.
NCMD / DCMD
A command from the host to a node or device, for example a setpoint write or a rebirth request.
NDEATH / DDEATH
The death certificate, registered with the broker as the MQTT Will so it is published even when the site cannot say goodbye.
seq
The rolling 0 to 255 sequence number on every message in a session, used to detect gaps.
bdSeq
The birth/death sequence number: a metric in NBIRTH and NDEATH that ties a death certificate to the session it belongs to, so a stale death cannot kill a newer session.

The Unified Namespace, Explained

One up-to-date picture of the plant that every system reads from. You get it as a result of publishing properly, with no second project to fund.

What comes as standard

It builds itself

Because each site describes itself when it connects, the picture fills in as sites come online. Anything new, a dashboard, a historian, an analytics tool, subscribes and finds what is there, instead of needing tag-by-tag configuration.

What SparkBridge adds

Plain JSON as well as Sparkplug

The Edge can also send the same values as plain JSON on a readable path, for tools that cannot read the Sparkplug format. Sparkplug for the systems that need types and connection state, JSON for the ones that just need a simple feed.

Beyond the Standard

Any conformant Sparkplug product gives you these four things. They are the baseline, and the real differences start above it.

What Sparkplug 3.0 already guarantees
Self-describing dataEach site publishes a birth certificate: every point with its name, type, units and current value.
Connection-state awarenessBirth and death semantics enforced by the broker, so stale values are marked rather than trusted.
Report by exceptionOnly changes move, so load tracks process activity rather than database size.
Typed equipment modelsA pump or a skid crosses the wire as an object with named members, not loose points.

Everything from here down is about what sits above that floor: what happens at scale, what you can measure, and what you pay as the estate grows.

why sparkbridge

Why SparkBridge

Eight capabilities built to take MQTT further, with more efficiency, more scale, and an architecture that holds up as Sparkplug moves to MQTT 5.

Shared-subscription scale-out. Four consumers share one broker stream and deliver about 20x the ingest of one. We have found no competing Ignition module that removes the single-subscriber ceiling.

Published, measured numbers. Load and endurance scenarios you can run yourself, with the hardware stated. No competing module publishes comparable figures.

Change settings without a restart. Configuration hot-reloads in about five seconds. No scheduled outage to add a site or change a deadband.

Metadata folding. Units, ranges and descriptions ride the birth certificate instead of the data stream, taking roughly a third of points out of steady-state traffic.

Per-site scoping as standard. An edge credential is locked to its own site. It cannot issue commands, and it cannot write another site's data. Proven live against the broker, with the file-RBAC equivalent generated for estates on external HiveMQ.

No client-count tiers. The broker is not licensed by how many clients connect, so there is no 50 or 250 ceiling to design around.

Warm-standby hosts. Standbys hold live state and take over by rank, measured at 244 ms across 25 nodes with no edge rebirths. The estate does not notice the handover.

Signed fleet configuration distribution. Configuration reaches every gateway as a signed bundle, so a site can prove what it was told to run and refuse anything it cannot verify.
