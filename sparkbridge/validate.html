Stop writing the document. Generate it from the code.

Validated industries spend weeks by hand on document sets that almost entirely restate what the PLC program and the Ignition project already say: what an alarm's setpoint is, what rung writes a tag, which view shows it, what the interlock does. SparkValidate reads the L5X/L5K export, the Ignition tag and project exports, or a live gateway, and builds one normalized system model with a stable ID on every entity, so the requirements, the design spec and the test protocols can all point at the same source instead of being retyped three times.

Risk drives scope, not habit. Each function and component gets a risk assessment: severity, probability and detectability roll up to a risk class, and the class sets the test depth, full challenge test with boundary values at high risk, functional verification at medium, a documented rationale for skipping at low. Every skip is written down and defensible, because a regulator asking "why wasn't this tested" gets an answer that already exists in the RTM.

The alarm side gets the same treatment under ISA-18.2. Every alarm becomes a Master Alarm Database row: cause, consequence, operator action, allowable response time, priority from a consequence/time matrix, classification. The alarm journal gets read for the KPIs that matter, alarms per ten minutes, percent time in flood, the standing and bad-actor lists, so rationalization starts from what the plant is actually doing, not from a blank template.

Ingest to Evidence, One Pass

Six stages, all built on the same system model, so nothing downstream is retyped from what upstream already established.

StageWhat happens
1. IngestReads the L5X/L5K program export, the Ignition tag export, the Ignition project export, or connects to a live gateway for the same facts plus runtime state, module versions and licenses.
2. System modelCross-links every entity: an OPC tag path to the PLC tag it maps to, the rung that writes it, the views that show it, the alarms on it. Every entity gets a stable ID the rest of the pass points at.
3. RiskRuns the GAMP-consistent risk assessment and the ISA-18.2 alarm rationalization against the model, against a risk policy you can configure in YAML to match your own QA procedure.
4. Documents and protocolsGenerates all 13 documents and the executable test protocols from the risk-scored model, at the depth the risk class calls for.
5. EvidenceThe gateway module executes IQ, OQ and alarm test protocols against the running system, capturing screenshots, config hashes and journal rows, sealed into a tamper-evident package with a re-auth e-signature.
6. GitHubThe model, requirements, MAD, protocols and RTM live as text in your repo. Regenerating on a pull request shows exactly which requirements and tests a change affects, and a check can fail the build if coverage drops.
alarm management

Rationalization Starts From What The Plant Is Doing

ISA-18.2 sets the shape of a Master Alarm Database. SparkValidate fills it from the code and the journal instead of a blank workshop.

Every alarm found in the L5X (ALMD, ALMA) or the Ignition tag config becomes a MAD row with a cause, a consequence, the operator action, the allowable response time and a priority derived from a consequence/time matrix you can configure. Setpoint basis, classification (safety, environmental, quality, production) and shelving state are captured alongside it.

The alarm journal gets read for the KPIs ISA-18.2 defines: alarms per ten minutes, percent time in flood, priority distribution against the roughly 80/15/5 target, and the standing and bad-actor lists. Chattering and stale alarms are flagged automatically from journal statistics, and duplicate alarms across tags are called out before they become two rows in a workshop meeting.

The Alarm Test Protocol then exercises every alarm in the database, not a sample: annunciation, priority display, ack, shelve, pipeline delivery and journal record, executed against sim tags or a gated PLC write with explicit permission, with the result captured as sealed evidence.

What The Frameworks Mean Here

Worded carefully on purpose, because a validated site's auditor will read this page.

The risk approach and document set are built consistent with GAMP 5 (2nd edition): software category classification, a risk-based test depth, and a document set shaped like the one a GAMP-based quality system expects. SparkValidate is a tool that produces the evidence and the documents; it does not replace your quality system, your SOPs or your QA sign-off, and it does not itself certify compliance with anything.

21 CFR Part 11 applicability is conditional on your own regulatory context and how you configure and operate the system: the gateway module provides the hooks, executed-by identity from Ignition auth, timestamps, reason-for-change capture, e-signature via re-authentication, and an audit trail written into the Ignition audit profile, but whether your deployment meets Part 11 depends on your validation of those controls in your environment, not on the module alone.

ISA-62443 is used for the security risk assessment structure: zones and conduits, roles and permissions, and a target security level per zone, extracted from your Ignition security configuration and network facts. This is a risk assessment output, not a certification against the standard.
