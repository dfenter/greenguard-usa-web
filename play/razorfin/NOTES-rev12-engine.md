# NOTES-rev12-engine.md — Rev 12 engine3d.js lane (zoom, modes, level ctx)

Owner: engine3d.js only (per SPEC3D.md 12.6: camera, modes, level ctx, super
size). Data (LEVELS/MODES/PICKUPS/cls/Sharkjira rename) is gen_data.py/data.js,
regenerated by a parallel lane; every number/shape below is READ from
`RFD.MODES`/`RFD.LEVELS`/`RFD.LEVEL_BY_ID` with a matching built-in default so
the game runs identically whether or not that data has landed yet.

## 12.5 — Zoom + bigger sharks

- `CAM_Z_LEN_MULT`: 1.75 -> 2.2 (dolly out ~25%).
- `CAM_Z_MIN`/`CAM_Z_MAX`: 200/450 -> 250/600.
- Framing selftest gate: `sharkLenPx / (CAM_FRAME_TAN2 * z)` accept band
  moved [0.28, 0.34] -> [0.20, 0.28] to match the wider dolly (verified for
  len factors 0.9 through 2.6: fraction ranges 0.2212..0.2662, all inside
  the new band — see engine3d.js's own selftest for the tier 1/6/12 check).
- `mouthRadiusForLen` upper clamp: 90 -> 100 (base mouth radius at len 2.6
  is ~70.9px, well inside the new clamp with headroom).
- `p.r` (body radius) has no clamp and scales linearly with `sil.len`, so it
  needed no change; it is also the range basis for `LUNGE_RANGE_MULT`,
  `PREY_NEAR_RANGE_MULT`, and the world-edge clamp, none of which needed
  touching.
- Pursuit dead-zone (`CTL_PURSUIT_DEAD_NOSE_MULT`/`CTL_PURSUIT_DEAD_CSS_MAX`)
  derives `noseRcss` from `liveWorldPerCssPx()`, which reads the LIVE
  `camera.position.z`/`fov` every step — it already self-corrects for the
  wider dolly with no code change. Verified live via
  `scratchpad/razorfin/touchprobe.js` (dive/ascend both settle to a clean
  ±1.57 rad heading, vy ~288, camZ 273 for a tier-1 reef shark — inside the
  new 250..600 clamp) and `sdfprobe.js` (dive track descends smoothly, no
  NaN/errors).

## 12.4 — Modes / power-ups

New config block `MODES` (mirrors `RFD.MODES` / `data.js`):

```
MODES.goldRush     = { dur: 8,  coinMult: 2, speedMult: 1.3(*), invulnerable: true, tint, banner }
MODES.megaGoldRush  = { dur: 10, coinMult: 3, speedMult: 1.5, invulnerable: true, allEdible: true, tint, banner }
MODES.buffs.supersize = { dur: 10, sizeMult: 1.5, tierBonus: 2, tint }
MODES.buffs.shield     = { dur: 12, hits: 3, tint }
MODES.buffs.speed      = { dur: 9, speedMult: 1.5, tint }
```
(*) engine3d.js's own built-in fallback for `goldRush.speedMult` is 1.3 per
the son's spec ("speed x1.3"); the currently-landed data.js ships 1.4 for
that same field — data.js wins whenever it is present, since it is the
source of truth (12.6).

### State machine

`ctx.run.mode` is one of `''`, `'goldRush'`, `'megaGoldRush'`. It is a pure
projection of the existing `goldRushT` timer + a new second meter
(`ctx.run.megaMeter`, 0..1) that only fills while `mode === 'goldRush'`:

```
frenzy meter (ctx.run.frenzy) fills 0..1 from eats (existing, unchanged)
  -> reaches 1: goldRushT = MODES.goldRush.dur, mode = 'goldRush',
     banner via uiCall('chip'/'notice'), +1 power charge (existing hook)

while mode === 'goldRush':
  - swallow() fills megaMeter instead of frenzy (frenzy stays pinned at 1)
  - coinMult = MODES.goldRush.coinMult (2x)
  - speedCap gets MODES.goldRush.speedMult on top of everything else
  - stepPlayerHits invuln gate (unchanged: goldRushT > 0 covers both modes)
  - megaMeter reaches 1:
      -> mode = 'megaGoldRush'
      -> goldRushT = max(goldRushT, MODES.megaGoldRush.dur)  (never SHORTENS
         whatever was left of the current window)
      -> megaMeter resets to 0, banner announced once (_megaAnnounced)
      -> eatEligible() returns true for EVERY non-hazard prey (allEdible)
      -> coinMult = MODES.megaGoldRush.coinMult (3x)
      -> speedCap gets MODES.megaGoldRush.speedMult instead of goldRush's

goldRushT decays every step; hitting 0 clears EVERYTHING in one edge:
  mode = '', frenzy = 0, megaMeter = 0, goldRush.{meter,t} = 0,
  _goldRushAnnounced = false, _megaAnnounced = false
```

`ctx.run.goldRush.meter` (the HUD-facing gold bar) shows `megaMeter` while
any gold mode is active (so the bar reads as "progress to the next chain
step"), and the primary `frenzy` meter otherwise.

### Speed multiplier: moved out of applyFrenzyMults

Previously Gold Rush's speed multiplier lived inside `applyFrenzyMults()`
(folded into `p.st.statMults.speed`, `Math.max(goldSpeed, bloodSpeed)`
against Blood Frenzy so the two never compounded). Rev 12 needs THREE
speed sources that can all be live simultaneously (mode, the SPEED pickup,
Blood Frenzy) without hand-written max()/ratio tricks, so:

- `applyFrenzyMults()` now applies ONLY Blood Frenzy's speed/bite. Gold/Mega
  Gold Rush speed no longer touches `statMults.speed` at all.
- `stepControl()`'s `speedCap` computation gained its own `modeSpeedMult`
  term (resolved straight from `ctx.run.mode`) and a `pickupSpeedOn` term
  (the SPEED pickup, `ctx.run.buffs.modeSpeed`), both multiplied straight
  into `speedCap` alongside the existing `speedM`/`boostM`/overdrive terms.
  All multiplicative — they compound by design (mode + pickup + overdrive
  can all stack).

### Power-ups (pickups)

- New pickup ids from data.js `PICKUPS`: `buff_supersize`, `buff_shield`,
  `buff_speed`. Handled in `applyBuffPickup()` alongside the existing six.
- **SUPER SIZE** (`ctx.run.buffs.supersize`, timer): folds into `eatEligible`
  via `supersizeTierBonus()` — the SAME single gate formula megajaw uses
  (`p.tier + BITE_UP_BASE + biteUp + megajawBiteUp() + supersizeTierBonus()`),
  not a second gate. Visually/physically: `p.rBase`/`p.mouthRBase` are the
  shark's true radii (set once in buildPlayer); `stepSuperSize(p)` runs first
  in `step()` every frame and writes the LIVE `p.r`/`p.mouthR` as
  `base * (supersize > 0 ? sizeMult : 1)`. The rig's on-screen scale is set
  once, in `renderPlayer()`, as `g.__baseScale * eatPop * superSizeScale` —
  folded into the SAME scale write the eat-pop already owns, so a
  super-sized shark's eat-pop still reads as a small flourish on top of the
  sustained bigger size rather than two writes fighting each other.
- **SHIELD** (`buff_shield` -> `ctx.run.buffs.modeShield`, a SEPARATE charge
  counter from the legacy `buffs.shield`): `stepPlayerHits` absorbs from
  `modeShield` first, then falls back to the legacy `shield` charges if that
  runs out. The two power-up tables can never stomp each other's charges.
- **SPEED** (`buff_speed` -> `ctx.run.buffs.modeSpeed`, a timer): plain
  multiplicative `speedCap` term (see above), decays in `stepBuffs` like the
  other timed buffs.
- `MOUTH.eligibleTierMax` (the world-facing "can this eat that" descriptor)
  and the HUD (`hudState`, buff bars, `mode`/`megaMeter` fields) both mirror
  the same rules.

### uiCall wiring

Mode transitions call `announceFrenzy()` (existing `chip`+`toast` combo) AND
`uiCall('notice', banner)` so the HUD banner law in the task ("HUD banner via
uiCall('notice'/'chip')") is satisfied without inventing a new bus message —
`uiCall` already no-ops safely if `RF.UI.notice` is not implemented yet.

## 12.1 — Level ctx

- `ctx.level`: resolved once per run in `buildContext()` via a new
  `activeLevelId()` helper — reads `profile.selectedLevel` if it names a
  known `RFD.LEVEL_BY_ID` entry, else the first `RFD.LEVELS[0].id`, else the
  hardcoded default `'hawaii'`. `ctx.run.level` mirrors the same value (some
  meta.js code reads `ctx.level || run.level || profile.selectedLevel` — see
  meta.js:984 — so both fields carry it).
- `RF.World.init(scene3, ctx)` already receives the whole `ctx` object as its
  options bag, so `ctx.level` reaches world3d for free — no signature change
  needed on that call.
- `RF.Game.selectLevel(id)`: new export. Delegates the actual persisted
  choice + unlock check to `RF.Meta.selectLevel(profile, id)` (meta.js owns
  `profile.levels`/`selectedLevel`, the save schema v3 migration, and the
  unlock gate). If `RF.Meta` is not loaded (defensive: level select UI may
  land before/without that lane), degrades to writing `profile.selectedLevel`
  directly whenever `id` is a recognised `RFD.LEVEL_BY_ID` entry. Either way,
  on success it also syncs a LIVE run's `ctx.level`/`ctx.run.level` in place
  so switching levels from a paused menu does not require a page reload to
  take effect on the next `startRun`.
